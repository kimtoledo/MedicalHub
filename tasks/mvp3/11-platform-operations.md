# Platform Operations Maturity

> **Status:** 🔵 Active — support/export baseline, real export generation, feature-flag rollout, per-tenant maintenance mode, scoped support-access enforcement, retention review flagging, and security-alert detection delivered; backup/restore drills and operational dashboards remain

---

## What & Why

As Dentra.ph scales, the platform team needs proper tooling to support clinics, respond to incidents, and maintain compliance — without Super Admin having routine access to patient clinical records.

---

## Done looks like

- ✅ **Support tooling:** Support agents have a scoped access mode. Accessing a tenant's records for support requires a written justification and generates an audit entry — no silent access.
- ✅ **Tenant export/offboarding:** A clinic can request a full data export (structured JSON/CSV). The clinic can be deactivated (archived); actual deletion/anonymization execution is a deliberate separate step (see retention automation below) requiring a human decision, per the user's choice not to auto-delete.
- ✅ **Retention automation (flag-only, by design):** archived clinics past a 90-day review window are automatically flagged for a Super Admin to review — the user explicitly decided against auto-deletion/auto-anonymization, so this stops at flagging plus recording intent (`anonymize_requested`/`delete_requested`), never performing the action itself.
- **Backup and restore testing:** Regular backup verification via restore-to-staging tests; all incidents are documented. Investigated and confirmed blocked — no backup mechanism (pg_dump, hosting-provider backup, or otherwise) exists anywhere in this deployment yet; building "restore drill" tooling with nothing to restore from isn't meaningful. The user declined to have one built speculatively pending a real backup-infra decision.
- **Operational dashboards:** Internal dashboard showing platform health: active clinics, API error rates, slow query alerts, and storage usage. Active-clinic count already exists (`activeClinics()`); error rates/slow-query/storage are genuinely new observability work, not yet started.
- ✅ **Security alerts (one real detector delivered):** flags a single actor whose mutation audit events touched an unusually large number of distinct entities within a short window — derived entirely from the existing immutable audit trail, no new read/access instrumentation. "Unusual login geography" is explicitly not covered — it would require a geo-IP dependency this doc doesn't scope, and reads are not currently audited at all (only mutations), so a "bulk record access" detector in the read sense isn't derivable from existing data without a separate, larger instrumentation decision.
- ✅ **Feature-flag rollout:** Ability to enable new features for a subset of clinics before full release.
- **Migration and maintenance tooling:** Safe schema migration scripts with rollback plans; ✅ per-tenant maintenance mode.

### Delivered baseline

- Added written-justification support-access requests with Super Admin approve/deny decisions, 30-minute approval expiry, and immutable audit events.
- Added tenant export/offboarding request metadata with clinic-admin submission and Super Admin processing state controls; no export artifact or deletion runs silently.
- Added a protected platform operations clinic inventory endpoint to support future health/retention dashboards.
- **Real export generation (this update):** `generateExport` now gathers ~24 clinic-scoped tables (patients, appointments, encounters, treatment plans/records, invoices and their line items/payments/transactions, prescriptions, odontogram events, clinical file metadata, reviews, HMO payers/memberships/claims, and inventory), assembles a structured JSON document with an explicit manifest of what's included, and uploads it to the same object-storage bucket clinical files already use (`exports/{clinicId}/{requestId}.json`).
- Uploaded file *binaries*, staff/user accounts, and audit logs are explicitly excluded from the export document (listed in the document's own `excludedFromExport` field) rather than silently omitted — file binaries remain retrievable individually via the existing per-file signed URLs.
- Added a signed-token download flow reusing the exact HMAC token scheme from clinical file downloads: a Super Admin or the requesting clinic's own admin can mint a short-lived download URL (`GET .../exports/:requestId/download-url`), and the actual bytes are served from a token-gated, session-free `GET .../exports/:requestId/download` route — mirroring `clinic-files.ts` exactly.
- `markExport` no longer accepts `ready` as a manually-set status — only `generateExport` can reach `ready`, since it's the one that actually produced an artifact; manual `processing`/`failed`/`cancelled` transitions remain for cases requiring human override.
- Minting a download link and generating an export are both audited (`TENANT_EXPORT_GENERATED`, `TENANT_EXPORT_DOWNLOAD_LINK_ISSUED`) given the sensitivity of a full clinic-data extraction capability.
- Investigated scoped support session enforcement (below) before this was buildable: the approval flow (`supportAccessRequests`, 30-minute expiry) was a request/audit record only — nothing queried it to gate access. Super Admin unconditionally bypassed `hasClinicAccess` on some route families (hmo, remote-consults, entitlements, clinic-ai), and had **no** access path at all on others (clinic-patients, clinic-encounters via `requireClinicFeature`).
- **Feature-flag rollout (this update):** new `feature_flags`/`feature_flag_clinics` tables let a Super Admin create a flag (a `key` + display name) and either target it at a specific subset of clinics or flip it to `enabledByDefault` for a full release. `isFeatureEnabledForClinic(key, clinicId)` is exported from `operations-service.ts` for future application code to gate behavior by flag — creating/targeting a flag here only controls *who* it applies to; a flag key doesn't do anything until some other feature's code calls that check. New endpoints: `GET/POST /v1/admin/operations/feature-flags`, `PATCH .../feature-flags/:flagId` (rollout toggle), `POST/DELETE .../feature-flags/:flagId/clinics/:clinicId` (subset targeting). Minimal UI added to the Super Admin operations console. Verified all four states (untargeted, targeted, removed, full rollout) end-to-end against a real seeded clinic.
- While generating this feature's migration, hit the exact same silent-migration-skip class of bug as the earlier service-catalog migration, but one level deeper: drizzle's migrator picks the single `max(created_at)` already recorded and only applies journal entries whose `when` exceeds it — the earlier session's manual reconciliation had left that max slightly ahead of "now," so the newly generated migration (with a real, smaller `when`) was silently skipped again despite `db:migrate` reporting success. Root-caused it all the way to two anomalous entries in `packages/db/migrations/meta/_journal.json` (`0013_hmo_claims`/`0014_merge_history_reconciliation` carry `when` values further in the future than every migration up through this one) and fixed it for good by renumbering every journal entry's `when` and the matching `__drizzle_migrations.created_at` row to a clean sequential integer sequence (1, 2, 3...) — small integers can never collide with a real future epoch-millisecond timestamp, so this class of bug should not recur. Confirmed via direct hash/table inspection against the dev database (with the user's explicit approval before running the raw `UPDATE`).
- **Per-tenant maintenance mode (this update):** the user decided the semantics — block writes only (reads keep working), and Super Admin/support access is never affected. Added `clinics.maintenanceMode`, a boolean orthogonal to `clinics.status` (deliberately not a new status enum value, so it never interacts with `allowedClinicStatusTransitions`' existing lifecycle rules). Enforced at the single chokepoint identified in the earlier investigation — `requireClinicFeature` in `clinic/access.ts`, which already resolves the clinic's entitlements/status on every call — by rejecting `POST`/`PUT`/`PATCH`/`DELETE` requests with `423 CLINIC_MAINTENANCE_MODE` when `maintenanceMode` is true and the caller isn't a Super Admin; `GET` requests and Super Admin requests of any method pass through untouched. This covers every route family that already goes through `requireClinicFeature` (patients, encounters, treatment plans/records, odontogram, inventory, staff, service catalog, reports, billing, etc.) — route families that only use raw `hasClinicAccess` directly (hmo, remote-consults, entitlements, clinic-ai) are not yet covered by this pass. Super Admin toggles it via `PATCH /v1/admin/operations/clinics/:clinicId/maintenance-mode`; the operations console shows clinics currently in maintenance with a one-click "Turn off," plus a collapsed list to turn it on for any other clinic. Clinic staff see a banner in the app shell while their clinic is in maintenance. Verified end-to-end against a real seeded clinic (before/during/after toggle), plus route-level tests confirming a write is blocked with 423 for a normal clinic member, a read still succeeds, and a Super Admin's write still succeeds.
- **Scoped support-access enforcement (this update):** the user decided the scope — ALL clinic-scoped data routes require a grant, not just a subset. Added `hasActiveSupportGrant(db, authorization, clinicId)` in the new `auth/support-access.ts` — true only for a Super Admin with an `approved`, unexpired `supportAccessRequests` row for that exact clinic, requested by that exact caller. Replaced the unconditional `isSuperAdmin(...)` bypass with this grant check across every clinic-scoped data route family: `hmo.ts` (11 call sites), `remote-consults.ts` (5), `entitlements.ts` (1), and `clinic-ai.ts`'s `checkDentistAuth` (3). Also extended `requireClinicFeature` in `clinic/access.ts` — the shared chokepoint for ~17 route files (patients, encounters, treatment plans/records, odontogram, inventory, staff, service catalog, reports, billing, files, dashboard, analytics, recalls, prescriptions, ai-imaging, online-payments) — with the same grant fallback when the caller has no clinic membership, extending real Super Admin coverage to route families that previously had none at all. `db?: DB` threaded through every affected route registration's options and `app.ts`'s wiring so the check has something to query. Verified the grant-check logic directly against a real seeded clinic through all its states (no grant, pending, approved+unexpired, approved+expired) — all resolved correctly — plus the full existing test suite (398 tests) passes with no regressions, confirming normal clinic-member access paths are untouched.
- **Retention review flagging (this update):** the user decided against any actual auto-deletion/auto-anonymization — this is a non-destructive review queue only. Added `clinics.archivedAt` (set when `status` transitions to `archived`, cleared on reactivation — a real queryable column now, rather than only derivable from the audit log) and a new `data_retention_flags` table. A scan (boot-time sweep, mirroring this codebase's only existing recurring-job pattern, plus an on-demand "Scan now" in the console since no cron infrastructure exists here) finds archived clinics past 90 days with no existing pending flag and creates one. A Super Admin resolves a flag with a required note: keep the clinic, or record an anonymize/delete *request* — no code path here performs the actual anonymization or deletion, which remains a deliberate separate, human-driven step. New endpoints: `POST /v1/admin/operations/retention/scan`, `GET /v1/admin/operations/retention`, `POST .../retention/:flagId/resolve`.
- **Security-alert detection (this update):** one real detector, derived entirely from the existing immutable `audit_events` table — no new instrumentation. Flags when a single actor's mutation events touch more than 50 distinct entities within a rolling hour (severity escalates to `critical` past 100). New `security_alerts` table; same boot-sweep-plus-manual-scan pattern as retention. Caught and fixed a real dedup bug during verification: the scan's "already-alerted" check compared the new scan's window start against the existing alert's window start, which — since a fresh scan's window is always later — meant the dedup check never actually matched, letting a duplicate alert through on every rescan; fixed by checking only alert status (`open`), which is what "already alerted and not yet resolved" actually means. Verified the fix directly against real seeded data (manufactured audit events, confirmed no duplicate on rescan, confirmed a fresh alert raises again only after the prior one is resolved). New endpoints: `POST /v1/admin/operations/security-alerts/scan`, `GET /v1/admin/operations/security-alerts`, `POST .../security-alerts/:alertId/resolve`.
- Verified 428 passing API tests, repository-wide TypeScript checks, and production web/API builds.
- Remaining: backup/restore drills (blocked on a backup-infra decision the user declined to make speculatively), and operational dashboards for API error rates/slow-query/storage usage (genuinely new observability work, not yet started).
